## 一、故障复盘：声音克隆「样本试听」播放按钮灰色、无法播放

### 1.1 现象
- 在"声音克隆"页选择声音样本后，`<audio>` 播放条**一直灰色**、点不动。
- 修改一天（期间反复改"取音频机制"）仍未修复。

### 1.2 真实根因（一句话）
>`useVoiceCloneStudio` 里 **定义并赋值的两个响应式 ref（`samplePreviewUrl`、`samplePreviewLoading`）没有放进 `return` 对象**。组件解构后恒为 `undefined`，模板 `:src="samplePreviewUrl || undefined"` 永远算出 `undefined`，`<audio>` 元素**从未获得 src** —— 所以播放条永远灰色、无法播放。

### 1.3 因果链（关键）
```
useVoiceCloneStudio.ts
  定义 samplePreviewUrl  = ref('')            ← 存在（L241）
  loadSamplePreview() 内 samplePreviewUrl.value = abs   ← 赋值成功（L277），函数内 log 显示"播放地址=http://…"
  但 return { … } 不含 samplePreviewUrl/samplePreviewLoading   ← 【致命缺口 L778-793】
        ↓
VoiceClone.vue
  const { samplePreviewUrl } = s             ← s.samplePreviewUrl = undefined（未暴露）
        ↓
模板 <audio :src="samplePreviewUrl || undefined">   ← undefined → src 从未设置
        ↓
<audio> readyState=0 · 播放按钮灰色 · 无法播放
```

- **函数内日志是"正常"的**：`loadSamplePreview` 确实算出并设置了 `samplePreviewUrl.value`（日志："播放地址=http://192.168.111.31:8000/voice/samples/456/audio"）。但这只是**闭包里的 ref**，组件那一侧绑定的是另一个 `undefined`。
- **传输层从头到尾没坏**：用真实 Electron（31.7.7，同 CSP、同 `file://` origin）做探针复现，**直连服务端 URL** 与 **base64→blob URL** 两条链路、mp3 与 wav 样本，全部 `loadedmetadata / canplay / readyState=4` 正常播放、无 error。
- **所以改了一天传输层（base64↔blob↔直连）全无用** —— 因为值根本没到达 `<audio>` 的 src 上。方向错了，改哪一层都没用。

### 1.4 为什么一天没被类型检查拦住
- 构建用 **Vite/esbuild：只转译、不查类型**。`const { samplePreviewUrl } = s` 解构一个不存在的 key，**静默得到 `undefined`，零编译错误、零运行时异常**。
- `npm run typecheck`（tsc）本可拦截"解构了不存在的属性"，但当天没作为门禁强制跑，或没跑。

### 1.5 修复
- 在 `useVoiceCloneStudio.ts` 的 `return` 中加入 `samplePreviewUrl, samplePreviewLoading`（1 行）。
- 验证：`npm run typecheck` 通过；`npm run build:renderer` 通过；构建产物里 composable `return` 已含 `samplePreviewUrl`/`samplePreviewLoading`。

## 二、工程规范铁律

### 铁律 1｜Composable 的"定义 ≠ 暴露"：ref 必须显式 return
- 在 `use*()` 组合式函数里，**凡是要给组件用的 ref/computed/函数，都必须出现在 `return { ... }` 中**。
- **自检动作**：写完组合式函数，立刻跑一次
  ```
  # 列出组件解构的每个 key，逐一确认都在 return 里（人工或脚本）
  ```
  并在 `docs/` 提供一份"组件解构 ↔ 组合式 return"核对真值（本项目已加入 `audit-ipc-consumers.js` 同类机制，建议扩展成通用 `audit-composable-exports.ts`）。
- **反例即本故障**：内部 ref `samplePreviewUrl` 存在且被赋值，组件拿到的却是 `undefined`。

### 铁律 2｜模板绑定必须验证"值真的到达 DOM"，而非"函数执行了/算对了"
- 任何 `:src` / `:href` / `v-model` / `:value` 这类**最终驱动 DOM 属性**的绑定，排查时必须验证"绑定变量在渲染层的真实值"。
- **只信"值到达元素"的日志，不信"函数内部算出了值"的日志**。函数内 log 正常，不代表组件绑定拿到了。
- 排查顺序（先验证机制，再怀疑上游）：
  1. 给一个**确定可播的地址**，在真实渲染环境（同 CSP、同 origin）做最小复现；
  2. 确认该地址能播（`loadedmetadata` / `canplay` / `readyState>=4` / `error.code`）；
  3. 再往上查"地址/数据是否真的传到了绑定变量"。

### 铁律 3｜构建管线不查类型 = 假绿灯，typecheck 必须进 CI/门禁
- Electron+Vite 项目里，`vite build`（esbuild）**不做类型检查**；解构/调用不存在的成员会静默得到 `undefined`，构建仍"成功"。
- **强制**：`npm run typecheck`（`tsc --noEmit`）必须作为提交/打包前必过门禁，CICD 里拦截。
- 任何"改完了 build 通过"都不等于"类型正确"。

### 铁律 4｜先"最小复现"再"动手改"，严禁同时改多处
- 本次教训：一天内改了 3 种传输方式（IPC→base64→data:→blob；blob；直连 URL），**同时改多个变量**，导致始终无法确认"哪一处有效、哪一处无关"。
- **正确流程**：
  1. 用真实 Electron + 真实端点做**最小探针**，先锁定"机制可用/不可用"；
  2. 每次只改**一个**变量，改完立即验证；
  3. 未复现问题前，不批量重写。
- 排查媒体类问题时，**最小探针必须用真实 origin（`file://`/自定义协议），而非 `data:`/`about:blank`** —— 两者对 http 媒体的加载行为可能存在差异。

### 铁律 5｜诊断日志要"打到断点值"，每层留痕到具体值
- 日志不仅记录"做了什么"（`选择样本：id=456`），更要记录"断点处的实际值"：
  - 最终拼出的 URL（`播放地址=http://192.168.111.31:8000/voice/samples/456/audio`）
  - 元素的真实状态（`readyState / networkState / duration / error.code / currentSrc`）
  - 绑定变量的值（绑定层的 `src` 到底设了没）
- 本次正是"只打了函数内算出的 URL"，掩盖了"组件绑定层是 `undefined`"。**每层都要能看见值。**

### 铁律 6｜客户端字段必须与服务端契约逐字段对齐，缺失即显式报错，不兜底猜测
- `/voice/samples` 的音频字段 = `audio_url`（相对路径）；客户端 `samples[].url = s.audio_url`，**不做 `|| s.url` 之类的猜测兜底**（见 `loadCatalog` 注释）。
- 字段缺失/漂移 → 显式 `clientError` + 用户提示，**绝不静默 return 或猜字段**。
- 服务端响应字段、主进程 IPC 契约、preload 映射、渲染层类型声明**四处必须同值**（本项目已从 `server-proxy.js` 的 `API_ENDPOINTS` 到 `server-api.ts` 建立同值约束）。

### 铁律 7｜关键失败路径必须有 `clientError` 打点，禁止"静默失败"
- 任何用户可见操作（试听/上传/转写/生成/导出）的**每个失败分支**都要 `clientError(tag, msg, err)` + 明确提示。
- "没有报错日志" ≠ "没有 bug"，可能是**没打点**。补探针是排障第一动作（本项目 `clientLog.ts` 已统一封装，落到 `userData/logs/main.log` 并自动上报服务端）。
- 本次故障初期 `<audio>` 的 `@error` **无 handler、完全静默**，用户看到的只是"点了没反应"；`clientError` 打到日志后才暴露出元素层问题。

### 铁律 8｜组合式函数职责：state 与编排分离，纯逻辑下沉
- `useVoiceCloneStudio` 这类 runner 层**只做编排**；解析/构建等纯逻辑下沉到 `voiceCloneLogic.ts`（parser/builder 层），便于单测、避免编排层膨胀出隐蔽 bug。
- 新增页面功能请沿用法：**逻辑（纯函数可测）→ 组合式（编排+响应式 state）→ 组件（视图）**。

### 铁律 9｜每个操作必须有文档依据；无依据不得动工（2026-09-16 因剪映封面事故建立）
- **事故**（2026-09-16 用户实测）：剪映导出的首页索引登记里，为省字段枚举用 `templateEntry = store[0]` **克隆首页第一条草稿当模板**；`coverPath` 为空时回退继承他人 `draft_cover` → 用户草稿首页封面指向「剪辑模板」目录。两个操作在文档里**没有任何依据**（旧附录仅一句「克隆现有条目保真 schema，缺省即可」，无原因、无风险警示）。**凡「想当然」式实现，必在某天以事故形式还账。**
- **强制流程**：
  1. **动工前**：把操作依据写进对应文档（或在既有文档确认落点）。依据必须可归类：**①用户裁决；②原版/上游一比一（移植铁律）；③第三方权威（pyJianYingDraft 等）/服务端契约；④本机/服务端实测证据**。四者皆无 → **先上报用户裁决，不得自行发明**。
  2. **实现时**：代码注释引用依据（文档名/裁决日期/实测样本）。
  3. **收尾时**：在「操作依据追溯表」（《剪映互通整体方案_2026-09-12》附录 H）登记一行；未登记不得入档。
  4. **高风险操作清单**（必须有明确依据+风险说明，否则禁止）：克隆外部数据当模板/基线、硬编码占位值、静默兜底回退、改写他人数据文件（root_meta 等）。
- **依据分级速记**：用户裁决 > 原版一比一 > 第三方权威/契约 > 实测证据 > 工程习惯（最低档，使用必须显式标注「工程细节·无外部依据」并优先求裁决）。
- **反例即本事故**：`templateEntry = store[0]`（无依据·已废除）；`coverPath: ''` 硬编码（无依据·已废除）；「成功」=仅文件存在性（无依据·已改 `verifyDraftFolder`）。
